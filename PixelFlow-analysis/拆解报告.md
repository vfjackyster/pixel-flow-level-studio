# Pixel Flow! 0.37.1 安装包拆解
分析日期：2026-10-29。对象为用户提供的 Pixel+Flow!_0.37.1_APKPure.xapk，包名 com.loomgames.pixelflow，构建号487。

## 核心判断
1. 美术底层是 **Unity URP + 正交视角3D低模 + 2D UI**。像素图用可复用立体块搭建；统一颜色材料、卡通光照、描边和简化投影构成视觉方案。
2. 关卡主要由离线配置组织：**27个funnel，3500条记录，其中完整基础集合2700关、其他集合800条同号变体**。不能说是3500个独立关卡，也不能认定所有玩家都使用同一集合。
3. **确认客户端实现了失败后动态减难系统 LevelEase**：正常失败事件进入持久进度，建关处理器消费进度并修改关卡数据；有实际队列重排、机关简化代码。**包内代码兜底配置默认关闭，远端键为 level_ease_settings；本次没有线上配置或实机触发记录。**
4. 核心决策是“在有限容量下，安排哪些颜色、多少余弹的射手，在什么时机经过哪些可攻击边缘”。像素几何、队列顺序与传送带时序共同构成解题约束，不能只当颜色总量配平。

## 2. 关卡如何组织与设置
### 文件组织
`assets/Levels/manifest.json` 声明27个funnel；每组有 `<funnelId>.idx` 与 `<funnelId>/<关号>.json`。idx为“关号:32位十六进制值”，具体散列口径未确认。json内容实际是 `gzip:` + Base64 + gzip压缩JSON。

完整基础集合 `3db5681ee587345ad9a3cf8400a692d1` 含连续1–2700关。其他26组共800条同号变体。比较发现：671条队列不同、462条难度标签不同、626条普通像素布局不同；另有只改预览等元数据的情况。**这证明存在内容版本/分流承载方式，不能单凭文件认定其按失败切换。** 实际玩家funnel与远端发布状态未取得。

### 一关的主要参数
| 配置 | 作用 |
|---|---|
| Difficulty | 作者预设的难度标签；不是已证明的自动评分 |
| PixelImageData.width/height | 像素逻辑网格尺寸 |
| physicalWidth/physicalHeight | 布局物理尺寸，独立于像素数量 |
| pixels[{x,y,material,...}] | 普通目标坐标与颜色 |
| QueueGroup.shooterQueues[].shooters[] | 每列射手顺序；射手id、颜色material、弹药ammo |
| SlotCount / ConveyorLimit | 等待槽 / 传送带容量配置 |
| HasTimeLimit / TimeLimit | 整关计时开关与数值 |
| ConnectedShooters、Locks、各机关数组 | 射手连接、钥匙锁、目标耐久、管道、蛇、冰等规则数据 |
| Preview / contentHash / isValid / validationErrors | 预览、内容与编辑校验元数据，不能当可解性证明 |

基础2700关的数据范围：
- 网格宽16–123、高15–140；这些是各自范围，不代表最大关必为123×140。
- 2–5列队列，直接列出的射手4–157个。
- 全部SlotCount=5；2699关ConveyorLimit=5，仅2314关为6。
- 全部HasTimeLimit=false。这不消除传送带运动/射速的时序影响。
- 难度标签：Very Easy 10，Easy 1314，Medium 571，Hard 509，Very Hard 296。
以上均为包内值，未证明运行时不会覆盖。

### 配关的实质
由数据结构推断的制作链为：
**图案栅格化并分配材质 → 放机关及关联ID → 按各色目标需求拆分射手与弹量 → 排入多列队列 → 设置容量和难度标签 → 验关 → 发布进funnel并维护索引。**
这里的流程顺序是分析推断，未恢复完整编辑器。

第1关最清晰：16×15画布，180普通像素，两列共6射手，材质5和8各90目标；每色弹药40+40+10=90。
第100关说明机关也参与配平：直接队列总弹240、普通像素178；差62恰对应蛇Count=62。同材质16的100弹=38普通像素+62蛇计数。不能把机关弹药需求当“额外补偿”。

基础集合机关引入节奏的例子：8隐藏射手、14连接射手、30目标耐久、40钥匙锁、55门、70像素管道、85隐藏像素、100蛇、120墙、140蛋盒、171射手管道、200冰、290射手冰、500分裂。完整39类统计见 [机关清单](levels/mechanics.json)。这是当前基础集合的首次非空记录，不代表所有玩家实际教学次序。

详细数据：[关卡核查](levels/关卡核查.md)、[统计](levels/summary.json)、[同号变体](levels/variant-comparisons.json)、[第1关解码](levels/3db5681ee587345ad9a3cf8400a692d1-1.decoded.json)。

## 3. 是否有动态调整难度
### 已证明的客户端能力
不是仅发现“difficulty”字段，而是已追到非debug路径：
1. `LevelEaseSystemController.OnEnable` (0x2634db4) 订阅正常关卡失败和胜利事件。
2. 失败经过 `RecordFailure` (0x26350a0) 记录进度。尝试次数来源为 `LevelSessionInfoData.LevelAttempNumber`。
3. `BeginAttempt` (0x26315a4) 为关卡射手ID建立原始队列行列映射；失败时用剩余射手定位失败进度。`FailureRows` 指射手队列行，不能解释成像素画的行。
4. 正常建关处理器 `CreatorLevelSettingsEaseProcessor.Process` (0x262ef28) 调用 `LevelEaseSystem.EaseLevel` (0x262f000)。
5. 系统检查Enabled，选择处理区域/目标，执行机关简化和射手队列调整，再创建本次尝试记录。

已具体核查的写入效果：
- `ShooterQueueEaseHelper.Advance` (0x262d98c)：通过相邻交换，把选定射手向队首前移，并处理受牛图腾限制的情况。
- `ConnectedShooterFeatureEaser.Ease` (0x262d170)：调用连接数据的删除连接方法。
- `ShooterIceBlockFeatureEaser.Ease` (0x262e684)：降低射手冰块health，最低保留1。
还存在链条、隐藏射手、锤、槌、牛图腾等FeatureEaser；各类完整改写行为以代码专项证据为准，不统一描述成“全部删除”。

这是**按尝试/失败进度，在建关阶段修改关卡的减难机制**。本轮没有证明同局临时改命中率、暗增弹药、强迫失败或保证获胜。

### 参数与启用状态
配置入口通过设置助手读取键 `level_ease_settings`；取不到时走代码兜底。设置助手完整实现与线上实际值本次未取得。已核查兜底：
| 参数 | 值 |
|---|---:|
| Enabled | false |
| TotalTryCountForAllEase | 15 |
| 首个区间 | StartLevel=1，EndLevel=799 |
| StartTryCount | 15 |
| RowSpacingPercent | 0.1 |
| TopEaseProbability / BottomEaseProbability | 1 / 1 |

算法里 `HasEnoughFailures` 使用严格大于比较；减难进度使用 `clamp01((attemptCount-startTryCount-1)/totalTryCountForAllEase)`（含零值与边界分支），随机种子为 `levelNumber*1009+tryCount`。这些是代码规则，**不能直接换算成“线上连续失败15次必减难”**：兜底默认关闭、远端可覆盖，尝试次数起算也未实机核对。

结论应表述为：**客户端确有失败后动态减难实现；当前线上是否启用、哪些分组启用、实际阈值和强度，静态安装包尚不能确认。** 预设Difficulty、funnel变体、性能A/B测试与这条LevelEase链分别看待。

已进一步核查七类处理：连接和锁链解除、冰块降血、锤/槌关联射手前移、隐藏射手标记移除、牛图腾计数减少。选取还受位置概率、feature权重及easeProgress共同控制，不是每次必改。详见 [代码与动态减难证据](code/findings.md) 及ARM反汇编（selected-native.txt、extra-native.txt）。

## 4. 核心玩法解析
### 循环
多列射手队列 → 选择当前可用射手 → 在容量允许时投入外围传送带 → 根据位置自动选择可攻击目标 → 同色攻击并消耗弹药 → 余弹射手回到等待/再投入流程，耗尽射手释放占用 → 清空地图或进入失败结算。

具体回流、特殊射手与机关各有分支，不能将此抽象当所有时序的完整模拟器。

### 真正产生难度的约束
1. **边缘暴露**：目标选择会按射手所在侧和行列对齐，先取前方实心目标。内层颜色不是随时可攻击；先清哪种颜色会改变后续可达性。
2. **取用顺序**：队列后排射手不能无条件越过前排。眼下无效的颜色可能是拿到后续关键颜色的成本。
3. **等待与带上容量**：留着余弹有未来价值，但占位也有成本；当前可投放不代表投放后安全。
4. **弹量拆分与时序**：颜色总量相同，拆成几个射手、每个多少弹、经过目标时边缘是否已打开，会形成不同决策。
5. **机关依赖**：连接、隐藏、锁、冰、多耐久目标和管道改变可见性、可操作性、目标需求及释放顺序。

`TickShooter` (0x2693a34) 先找目标，再调用Shoot；找不到目标时不进入该开火调用。不能认为每绕一圈必消耗固定弹量。`FindFrontTargetBest` (0x2695190) 调用对齐行/列与 `FirstSolidsFromSideAxis`，证实空间布局参与解题。

失败也不能简化为“等待槽达到5个的瞬间立即失败”：`OnSlotsFullAtConveyorExit` (0x28c185c) 在出口事件检查可攻击性并选择失败分支，另有无法射击、计时、机关等控制。投射物结算、自动收尾与特殊回流未做逐帧实测。

**设计含义（推断）**：其核心是带空间可达性的顺序与容量调度。要复现，最先需要统一目标选择、遮挡、队列合法动作、余弹回流和失败结算；仅把颜色总弹配平、再随机排队，不足以保证可解或有趣。

更多调用证据：[核心玩法证据](核心玩法证据.md)。
