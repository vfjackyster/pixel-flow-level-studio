# 核心玩法还原与JSON核对

目标：验证导出的普通像素关卡JSON，在本地可运行的核心规则中是否表现为预期图案、队列、弹药和容量。

## 证据与实现的区别
包内静态证据见 ../PixelFlow-analysis/核心玩法证据.md 和 code/findings.md：
- TickShooter 先找目标再Shoot，无目标不调用开火。
- FindFrontTargetBest 使用所在侧、对齐行列及FirstSolidsFromSideAxis。
- 存在传送带容量、等待区、余弹返回、弹尽和在途投射物结算。
- OnSlotsFullAtConveyorExit参与失败判定，不能等同点击满槽立即失败。

本地perimeter-play-v1显式选定：
- 从左下入口沿左、上、右、下四侧顺时针运行，坐标原点在图案左下。
- 物理尺寸决定图案与路径边长比例；每个逻辑像素映射到对应物理单元。
- 同速运动，入口保持间距，带上人数不超过ConveyorLimit。
- 当前侧只检查所在行/列的首个实心目标；先判断颜色，再检查伤害预占。
- 普通目标一发一像素，子弹飞行0.14秒后命中。射手弹尽立即离带，最后一发仍在途时不提前判断弹尽失败。
- 未耗尽射手到出口，有槽则回槽；无槽阻塞0.5秒且无在途子弹后失败。清图优先判胜。
- 没有强行加入按历史失败修改关卡的逻辑，源JSON决定本局配置。
以上方向、速度、对齐、角落和失败时序均未获得原版逐帧验证，不能称为完全复刻。

## 导出到试玩的数据链
编辑稿 → EditorCore.exportLevel → JSON.stringify → JSON.parse → validate → PlayEngine.create → 独立运行时。
导出按钮和“试玩当前关卡”调用同一exportLevel函数，避免两套字段映射发生偏差。
外部JSON单独解析和校验，不被自动配平、重排或覆盖原编辑稿。
试玩要求非空普通像素关卡；非空机关、重复坐标、重复射手ID、越界和无效容量会被拒绝。

## 三项逐色守恒
每一颜色分别检查：
1. 剩余目标 + 已命中目标 = 初始目标。
2. 未取射手余弹 + 等待余弹 + 带上余弹 + 已发射 = 初始弹药。
3. 全部已发射 = 已命中 + 当前在途。
并检查运行时只读输入的语义结构没有发生变化。
内容比较使用规范化后的实际像素坐标、材质、队列顺序、ID、弹药、容量与物理尺寸；FNV-1a指纹只用于定位，不用它代替结构相等判断。

## 验证边界
16个引擎测试已通过，含可回放的成功轨迹。它们验证本地实现与约定一致，不证明约定等同原游戏。
未完全恢复所有原生方法及运行时条件，没有启动原APK进行逐帧对照。
JSON字段结构兼容分析样本，不等于可直接回写到APK，也不认证线上远端配置和内容散列。

## 记录格式
导出的试玩验证记录包括原始input、version、params、summary状态与统计、audit守恒、acceptedInputs操作时间点和events。
每个输入的tick以1/120秒计。重放从同一input和params创建独立实例，按tick顺序提交合法输入并逐步推进。
暂停不推进模拟时钟，播放倍速不改变引擎步长；重开清除本次轨迹，开始新局。

## 原版前10关
试玩窗口现已内置 Pixel Flow! 0.37.1 完整基础集合的第1至10关，也可导入“原版前10关”目录中的01.json至10.json。
原始图案、颜色、队列、弹药、隐藏标记和元数据均保留；来源与核查.json记录逐文件散列。
第8至10关含隐藏射手，后排显示问号，进入队首后揭示。这是本地机制还原，尚未与原客户端逐帧核对。
编辑器仍拒绝含隐藏机关的关卡编辑，避免编辑或重生成队列时丢失原始字段；这类关卡可以直接试玩。
本地速度、射击与失败时序仍为近似规则，测试通过不等于原版体验完全一致。
