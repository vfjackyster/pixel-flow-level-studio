1. 使用 REA 拆解 Pixel Flow! 0.37.1 XAPK：美术方案、渲染、资产规格、关卡组织、动态难度、核心玩法。

3. 解释图案与图腾队列各自承担的难度，以及两者如何共同作用。

5. 编辑时实时看到难度，提供有由来且可检验的公式。
6. 允许导入图片，像素化后取近似颜色，并适配目标宽高生成关卡。
7. 复现核心玩法，用试玩验证导出 JSON 是否符合预期。
8. 提取原版前10关为独立 JSON，并在试玩中体验。
9. 确认隐藏图腾是否会因难度改变真实内容。
10. 把整套工程和工作上下文上传到新建 GitHub 仓库；默认私有。

## 当前完成状态

- `pixel-editor/`：纯浏览器网页编辑器，画笔、橡皮、填充、矩形、框选、翻转、撤销/重做、队列排序、射手颜色和弹药编辑、逐色供需检查、JSON/PNG 导出、本地草稿。
- 图片入口：面积采样/透明度加权平均、映射到提取出的34色材质、限制用色、留边/裁切/拉伸；按目标需求生成配平队列。
- 难度面板：图案结构指标和简化调度模型，固定种子抽样、区间估计、失败/预算边界。模型与连续运动试玩不同，不能直接解释为真人胜率。
- 试玩：四侧前沿遮挡、同色射击、有限弹药、队首出场、传送带容量、余弹回槽、再次投放、清图获胜和失败处理；有暂停、速度调整、重开、JSON核对及操作记录导出。
- 前10关：来自0.37.1完整基础集合的1至10号，保存所有字段；单独 JSON、内置选择器和打包 ZIP 均已完成。
- 第8至10关隐藏射手：后排问号，到队首揭示；隐藏标记保留。编辑器拒绝编辑含这些机关的数据，试玩单独允许加载，避免重新生成时静默删除字段。
- 报告、美术示意、原生代码映射、反汇编、关卡统计及验证材料在 `PixelFlow-analysis/`。
- 早期独立研究在根目录 `puzzle-lab.mjs`、`generate.mjs`、`verify.mjs`、`results/` 和 `research-report/`；这些是 Bus Jam 风格合成子模型，不能拿来证明 Pixel Flow 的商业规则。

## 关键结论与证据等级

### 固定隐藏内容与减难

原版 JSON 的射手具有 `id`、`material`、`ammo`；`SurpriseShooters.Shooters` 只保存隐藏射手ID。例如基础第8关 ID1 固定材质9（黄色）、10发。
静态代码已确认 `SurpriseShooterFeatureEaser.Ease`（0x262ebc4）可从隐藏ID集合移除被选射手。已核查路径中未发现因此重新抽颜色或增发弹药。另有特定机关关联射手前移路径，不能描述成任意洗牌。
作用在建关/重载阶段；未证实同局实时更改隐藏内容。证据见 `PixelFlow-analysis/code/findings.md` 及 `selected-native.txt` 第7278行起。
当前网页试玩没有动态减难；隐藏内容始终由输入 JSON 决定，修改 Difficulty 标签不会重抽隐藏内容。

### 原游戏动态减难

已确认失败事件→进度记录→重新建关→LevelEase处理的静态链。可以简化部分机关；默认兜底配置 Enabled=false，远端键 `level_ease_settings`。
线上是否启用、分组参数、失败次数与实际强度未知。不能说“线上失败N次必减难”，也不能把多分流变体当作失败后换关证据。
Windows REA 的原生 provider 当时无法处理该 ARM ELF，后续原生证据来自保存的 ELF/IL2CPP 映射及 Capstone 反汇编；不是完整 C# 源码恢复。

### 试玩近似边界

本地默认固定1/120秒步进，从左下入口顺时针，一圈18秒，30发/秒，弹道0.14秒；出口满槽等待0.5秒且在途结算后失败。
方向、速度、对齐容差、角落、投射物及失败时序没有与原APK逐帧对齐。只支持当前基础像素和前10关隐藏射手，其他机关/道具未复现。
试玩从导出JSON重新解析为独立副本，不修改编辑稿；不会因为试玩通过把原生isValid设为true。
